# neptron-modeline

Safe Switchres wrapper, monitor profiles and the ODREN policy. From source geometry, profile and GPU capabilities it makes a list of candidate modelines, and the policy picks the mode a game gets. No I/O.

## Must never depend on

- Any NEPTRON crate except `neptron-types` and `neptron-switchres-sys` (normal dependencies). `neptron-safety` is a dev-dependency only.
- Any other crate as a normal dependency: the error types implement `Display` and `Error` by hand, not with `thiserror`.
- Any hardware crate, I/O of any kind.
- `unsafe`: the crate root carries `#![forbid(unsafe_code)]`. The raw calls live in `neptron-switchres-sys`. No features.

## Public API sketch

- `fn modelines(&SourceGeometry, &MonitorProfile, &GpuCaps) -> Result<Vec<Candidate>, ModelineError>`: the Switchres modelines with the default settings. `modelines_with(.., &Settings)` takes other settings.
- `Candidate`: a `Modeline`, the index of the range that made it, and the Switchres score (stretched, refresh off, scale, refresh difference) in integers.
- `Settings`: doublescan, refresh tolerance, super width, monitor aspect.
- `policy` module: the ODREN policy, below.

## The policy

`neptron_modeline::policy` decides which mode a CRT, a flat panel or a TV gets for a game, and where the game sits in it. It is pure: no I/O, no clock, no global state except the lock of the Switchres calls. Switchres calculates each modeline. The policy decides the rung, the refresh, the width and the fallback.

### API

- `fn decide(&SourceGeometry, &PolicySettings, &MonitorProfile, &GpuCaps) -> Result<Plan, PolicyError>`: steps 1 to 5.
- `PolicySettings`: `style` (the picture mode: `auto`, `native`, `2x`, `3x`, `4x`, `sharp`, `speed`, `fit`), `refresh` (`exact`, `exact_x2`, `force_50`, `force_60`), `horizontal` (`None` for the GPU default, or a strategy), the Switchres `Settings`, `tv_width` (`aspect`, `integer`, `fill`; TV only), `panel_scale` (`auto`, `integer`; flat panel only), `vertical` (`exact`, `fit`; turned source only), and `arcade` (the systems `arcade` and `neogeo`).
- `Plan`: the source after the rotation, the effective settings, the refresh targets that the profile does not cover (`skipped`), and `considered`, every candidate in preference order. Each `Considered` has its `Rung`, its `RefreshTarget`, and a `Proposal` or a `Dropped` reason with the rule name and the numbers. `Display` on `Considered` and `Dropped` gives one log line.
- `Proposal`: the `Modeline`, the `Placement` (crop, destination, filter, UI destination, whole-scale claims), the `Timing` (game rate, target, line rate, field rate, frames per game frame), the width rule (`HorizontalScale`), and the `Padding` when the mode has one.
- `fn choose(&Plan, validate) -> Choice`: step 6. The first proposal that the validator accepts wins. The refusals before it are kept.
- `fn switch_for(Option<&Modeline>, &Modeline) -> Switch`: step 7. `ScaleOnly` or `Modeset`.
- `fn notice(&Plan, &Considered) -> Option<Notice>`: step 8. `Notice::reasons` gives the `NoticeReason` values that the quick menu shows.
- `fn decide_shown(source, settings, profile, caps, validate) -> Shown`: steps 5 and 6 with one fallback. When the validator accepts no proposal of the picture mode of `settings`, it takes the plan of `auto`, then of `fit` (owner, 2026-11-19: Fill is the default where no mode finds a picture), and sets `Notice::fill_fallback`. A mode that has a picture never changes. The engine and `offer` decide through it.
- `fn offer(source, settings, scanlines, profile, caps, validate) -> Offer`: the one decision of what the display gives for a candidate. It returns `Offered` (plan, winner, notice, scanline outcome) or `Declined` with a `DeclineReason` and the winner shown in its place. `SmallerFillsMore` is set where the asked multiple validates whole at the winner's rate but ranks after a smaller step.
- `fn picture_choices(...) -> PictureChoices`: a `RowAnswer` for each option of the picture mode and refresh rows, as the pair that a pick stores: `Plain`, `ResetsOther` (a pick sets both rows) or `Declined`. `ChoicesWork` makes the same answers a few decisions at a time. `fn for_every_game(&[PictureChoices]) -> Option<PictureChoices>` merges the answers of several sources (`RowChoice::not_for_every_game`, `SomeGames`); Settings > Display uses it with `REFERENCE_SOURCES` (ten real shapes). The menus build their options only from these answers ([video-policy-cases.md, section 8.7](../../docs/spec/video-policy-cases.md#87-the-one-decision-offer)).

### The decision procedure

| Step | Function | What it does |
| --- | --- | --- |
| 1 | `take_source` | Width, height, refresh, scan. A game turned by 90 or 270 degrees swaps its axes, so its long side becomes lines. |
| 2 | `read_settings` | No strategy gives the GPU default: dynamic super width with a pixel clock floor, native width without one. A fixed width of 0 or wider than the GPU becomes the widest of 3840, 2560 and 1920 that the GPU sends. |
| 3 | `walk_ladder` | The rungs of the style. `auto`: native, 2x, 3x, 4x, interlaced 1:1, fitted. `native`: native, interlaced 1:1, fitted, never a multiple. `2x`: 2x, interlaced, fitted. `3x` and `4x` fall to the smaller multiples first. |
| 4 | `refresh_targets`, `shape` | The refresh targets in order, and per rung the lines (height times the factor), the scan and the base width. |
| 5 | `solve` | The width by the horizontal strategy, and the modeline from Switchres. |
| 6 | `choose` | The validator walks the proposals in order. |
| 7 | `switch_for` | A winner equal to the current mode changes only scale and crop. |
| 8 | `notice` | A notice when the winner is fitted, runs at another rate, replaced the width strategy, took double refresh on its own (`native`), is not on the style's own rung, hides lines by an overscan crop, or is padded. |

### Rules

- **Refresh.** A rate matches when the mode is less than `REFRESH_MATCH_MHZ` (5 mHz) from it ("matches to two decimals": no rounding to 0.01 Hz can tell the two apart). `exact` aims for the game's rate. `exact_x2` (each frame twice), `force_50` and `force_60` come first only where a range covers the rate; the game's own rate follows them. A game rate that no range covers becomes the nearest covered rate (`Nearest`). Before that, for every style, it gets twice its rate (`NativeDouble`) when a range covers that (a Mega Drive PAL game at 99.40 Hz on a tube from 50 Hz); else the covered rate nearest twice its rate, each frame twice, when that changes the speed less than the nearest rate once (Little Robin at 30 Hz: 59.94 Hz on `ntsc`). When the exact rungs give no mode at the game's rate (or the nearest covered one), they also run at the highest lower rate at which a range holds the game's lines (`window_target`: `arcade_25` holds 384 lines up to 60.000 Hz). They rank before the fit while they change the speed at most `EXACT_SPEED_MARGIN_PPM` (2 percentage points) more than the fit does (`speed_order`); above the margin the fit wins. On a profile of one field rate (`ntsc`, `pal`) a mode that misses the rate takes the next whole multiples of the width until one gives it to the millihertz. The last resort is the fitted rung at the rate that Switchres reaches (`Unmatched`).
- **Picture modes.** `auto` takes the best exact result for the monitor: native on 15 kHz, 2x on 31 kHz, and twice the rate (`Double`) when the refresh choice is `exact_x2` and a range covers it. `native` shows the game's lines 1:1 and never a whole multiple. Its walk: (a) the native rung at each refresh target, not padded; (b) the native rung at twice the game's rate (`NativeDouble`), when `display.refresh_policy` did not ask for double refresh and a range covers the rate (a 31 kHz monitor with a 120 Hz range shows 240p at 120 Hz); (c) rung 3, interlaced 1:1, where the lines fit no progressive range; (c2) the native rung with an overscan crop; (d) every padded exact mode, the fuller first; (e) the fitted rung. Double refresh keeps the game's speed, so `exact` allows it, and the notice sets `double_refresh`. `2x`, `3x` and `4x` walk the smaller multiples, rung 3, then the fit.
- **Ranges.** A profile with two or more ranges that cover the rate is also shaped range by range (`per_range`): each range gives its own border, capacity and interlaced window, and the proposal keeps the index of the range in the profile. Ranges have gaps (15 kHz holds 192 to 288 lines, 31 kHz 400 to 512): as one window, a 320-line vertical game would get a soft fit. A range whose fewest progressive lines are more than it holds at the rate adds no capacity.
- **Lines.** A rung asks for the game's height times its factor. Switchres must keep the lines, the scan and the width, and reach the target rate, else the candidate is dropped (`LinesChanged`, `ScanChanged`, `WidthChanged`, `RefreshMissed`). An interlaced game on a monitor with no interlaced range is shown progressive (480i as 480p). A timing that does not fit its `Modeline` field drops that candidate (`TimingOutOfRange`); any other solver error is an error of the profile or the settings and stops the plan.
- **Fitted rung.** Switchres fits the source to the profile. When that misses the target rate, the policy asks again for the most progressive lines a range holds at the rate (`floor(h_max / rate)` less the vertical blanking, at most the line limit). A 510-line source at 60.606 Hz on `pc_31_120` gets 502 lines at 60.606 Hz, not 510 lines at 59.848 Hz.
- **Borders.** Pixel exact has priority over a filtered fit. A progressive game (or its whole multiple) with fewer lines than the ranges allow at the target rate is centred with black borders in a mode of any height that a range holds at the rate (`border_lines`). The standard heights 224 and 240 (`BORDER_LINES`, times the factor on a multiple rung) come first. Else the mode gets the smallest height in range that Switchres does not pad: at least the game's lines, the range's minimum, and the lines that the minimum line rate forces at the rate (`forced_picture_lines`; below that Switchres puts lines in the front porch and the picture sits high). The black lines are the policy's own centred border. The mode width keeps the game's aspect. When no range holds a height at the rate, the rung is dropped (`NoBorderMode`). A Master System on `pc_31_120` gets 2x, 384 lines in 448; a WonderSwan on `generic_15` gets 144 lines in 221 at 65 Hz.
- **Padding (OP-026).** A mode is padded when the game fills less than `PADDED_FILL_MIN_PERCENT` (75 %) of the picture lines. A border mode counts its border lines as picture lines (`Padding::fill_permille`). The picture lines are the larger of the mode's active lines per field and `ceil(h_min / rate) - ceil(h_min * vertical blanking)`, for the range that made the mode at the target rate. On the EDID profile of a 30 to 71 kHz PC CRT, a 224-line game at 60.099 Hz has 480 picture lines: 224 is 47 %, so the mode that Switchres pads to 500 lines is padded, and 2x (448 lines, 93 %) or double refresh (224 of 230 lines) wins. On 15 kHz, 224 lines fill 93 % of 240.
- **Overscan crop.** When a progressive whole multiple `k` of the game's lines (native is `k` = 1) misses the lines that the ranges hold at the target rate (`progressive_capacity`), the policy hides `ceil((height - capacity / k) / 2)` source lines at the top and the same at the bottom. The bound is `OVERSCAN_CROP_MAX_LINES_PER_EDGE` (8 source lines per edge, the classic NES crop from 240 to 224), and at most 8 lines of a 240-line screen (`OVERSCAN_CROP_SCREEN_LINES`) as a share of the lines the range holds, rounded up: 9 of 256, 16 of 480. The picture stays pixel exact. The width is never cropped. The uncropped candidate stays in the plan with its reason, and the cropped one follows it. `Proposal::overscan_crop` holds the numbers, the placement's crop leaves the lines out (columns of a turned frame), and the notice gives `cropped_lines`. An odd miss loses one line more than needed: an NES on `arcade_31` (478 lines at 60.099 Hz) shows 238 lines at 2x, 476 lines, about 1 line off centre. Donkey Kong on `pc_31_120` (502 lines) shows 250 lines at 2x.
- **Picture modes.** `sharp`, `speed` and `fit` walk the rungs of `auto` ([video-policy-cases.md, section 8](../../docs/spec/video-policy-cases.md#8-picture-mode)). `sharp` puts every exact mode before the fit at any speed change (no `EXACT_SPEED_MARGIN_PPM`), and reads `vertical` as `exact` and `panel_scale` as `integer`. `speed` uses a margin of 0 in `speed_order`, takes no doubled rate of its own, and on a flat panel puts the mode nearest the game's rate first (after the fit only, in steps of 0.1 %). `fit` asks the fit (`Effective::asks_fit`) for every progressive source, as `vertical = fit` does for a turned one: the fitted rung takes the most progressive lines a range holds at the rate, also at the window rate, so a progressive game gets no interlaced fit where a range holds progressive lines. On a flat panel `fit` fills at every scale; a fill below `PANEL_FILL_MIN_SCALE_MILLI` carries `SoftReason::FillMode` (`SoftReason::Chosen` for `vertical = fit`). On a flat panel `native`, `2x`, `3x` and `4x` give their whole factor, or the largest smaller one that fits (`style_fallback`), with the rungs `Native` and `Multiple(n)`. `offer` declines `speed` on a TV and `sharp` where the winner is a fit (`mode_refusal`, which the notice's `style_fallback` reads too).
- **Small picture.** `SMALL_PICTURE_MIN_PERCENT` (60 %, owner, 2026-11-16). For every style but `native`, a progressive exact mode of at least 60 % of the picture lines ranks before every interlaced 1:1 mode; a smaller one ranks with the interlaced modes by its fill. The notice carries `small_fill_permille` below 60 %. The policy never takes a soft fit for a small picture.
- **Vertical games.** `vertical = fit` for a turned source drops every interlaced 1:1 mode and every exact picture below 60 % (`Dropped::VerticalFit`), and the fit is progressive. On a TV the interlaced rung drops; on a panel the game fills the height. `exact` (the default) is the rule of every other game.
- **Order.** An exact mode at the asked rate (`exact_x2`, `force_50`, `force_60`) ranks before every exact mode at another rate, for every style: no fill comparison and no crop overrides it. `NativeDouble` is not an asked rate. Within each of these two bands, `native` orders its exact entries in four groups (`native_key`): (1) the native rung with no crop and no padding, at every target in target order (asked rate, game rate, `NativeDouble`); (2) interlaced 1:1 with no padding; (3) the native rung with an overscan crop; (4) every padded exact mode, the fuller first, then by target. The fitted rung of every target follows both bands, then the last resort. The other styles put every exact rung before every fitted rung (a fitted mode at a doubled or forced rate never beats an exact mode at the game's rate), then the refresh targets in order. Within a target: exact rungs with no crop and no padding in ladder order, then the cropped multiples, then the padded exact rungs, the fuller first (`crt_plan`). A padded mode on 31 kHz thus loses to line doubling, and a handheld on 15 kHz is centred with borders.
- **Shape.** A CRT mode covers the whole 4:3 face. A source of another shape (a turned game, 3:4) gets the mode width at which its lines keep their aspect (`border_width`) on every exact rung and on the crop; its fit fills the height at the aspect width. A game wider than the face is bordered with the lines its aspect needs and takes no crop. When no range holds those lines rounded up, the tallest height a range holds that is short by less than one game pixel (`factor` lines) takes their place. No mode squeezes a game more. A 4:3 source (within one thousandth) keeps the game width.
- **Width.** The policy computes the width: Switchres gets no pixel clock floor and never doubles the width. Native: the game width (or the border width). Dynamic super width: the smallest whole multiple whose pixel clock is at least the GPU floor (the validator's bound), estimated from the last pixel clock, at most 16 calls, and stopped when the product does not fit `u32`. Fixed super width: the fixed width, with a sharp filter. A game wider than the GPU gets the GPU's widest mode, with a sharp filter. A native or fixed width below the GPU floor is dropped with `PixelClockFloor` (width, pixel clock, floor, widest GPU mode); the next entry is the same rung with the dynamic super width, marked `strategy_replaced`, because the screen must get a mode. A source wider than the GPU has no replacement.
- **Pixel clock.** A Switchres mode outside the line rates that the validator takes (from the lower of `h_min` and `h_max` less one field rate, up to `h_max`) first moves into them by lines of the vertical back porch, at the same field rate (`onto_line_band`): on a range of one line rate (`ntsc`, `arcade_25`) Switchres can end one line per field off. Then every CRT proposal gets a pixel clock in whole kHz (`Modeline::PCLOCK_STEP_HZ`, `whole_khz`, ADR 0009): the kernel's mode record holds kHz, and a display backend refuses any other clock and never rounds. The rates of the proposal are the rates of the final clock and totals, so the proposal is the mode that the validator judges and the kernel reads back. `whole_khz` tries Switchres's horizontal total, then up to 8 pixels more or less (taken from the back porch), and for each total the whole-kHz clocks around Switchres's line time, the nearer first. The rules for the change are in the doc comment of `whole_khz`. When no mode passes, the nearest whole kHz at Switchres's total is the proposal, and the validator judges it. On the golden list every winner keeps its rung and its mode size, and its field rate is at most 3 mHz from the rate before the change. A flat panel's listed modes are not changed.
- **Placement.** The crop is the whole frame, less the lines of an overscan crop. On a CRT the game fills the width at a whole multiple, or the fixed width, and its lines times the factor, centred when bordered; the fitted rung fills the active area. On a flat panel the game gets the largest whole vertical factor at which its display aspect fits, centred, at the core's aspect (`panel_placement`). `ScaleClaim` gives the whole factors that hold exactly. The filter is `Nearest` when both axes are whole, else `SharpBilinear`. On a panel only, an axis whose scale is at least 1, below 2 and not whole takes `Nearest` (`panel_filter`): sharp bilinear with a prescale of 1 is plain bilinear, and a panel picture must never be blurry (SNES hires 512x224 on 720p, PAL 576i on 1080p). A scale below 1 keeps sharp bilinear.
- **UI canvas.** The placement holds no UI rectangle. `ui_placement(kind, mode, canvas)` gives the `UiPlacement` (`dest` and `filter`, the values of `Scene::ui_dest` and `Scene::ui_filter`) of a canvas of the size `canvas` after its turn (`T`), in the mode it is given. A CRT: the full active area (`ui_dest_fill`). A TV: the largest whole factor across inside `TV_SAFE_WIDTH_SAMPLES` and the largest whole factor down, each at least 1, centred: 320x240 is 640x240 at (40, 0) on 240p and 640x480 at (40, 48) on 576i. A flat panel: one whole scale (`ui_dest_uniform`). `Nearest` when both scales are 1 or more, else `SharpBilinear`.
- **Turned UI canvas.** `ui_dest_turned(kind, mode, canvas, monitor_aspect)` gives the `UiPlacement` (`dest` and `filter`) of a canvas turned by 90 or 270 degrees for a screen turned on its side (`docs/spec/tate.md`, section 6.4). `canvas` is the turned size, 240 x 320 for the 320x240 canvas. A CRT: the canvas lines at the largest whole scale that fits the active lines (all of them when none fits), the width that keeps the shape on the face, centred. A TV: the same lines, the whole multiple of the canvas width nearest to the shape width inside `TV_SAFE_WIDTH_SAMPLES`, centred. A flat panel: `ui_dest_uniform` with the turned size. `Nearest` when both scales are 1 or more, else `SharpBilinear`. It places the canvas in the mode it is given and decides no mode: 448i on `generic_15` gives 240x320 at (178, 64), 1080p 720x960 at (600, 60).
- **Flat panel.** When the scale at which the game fills the height of the mode (or its width, when the width comes first) is at least `PANEL_FILL_MIN_SCALE_MILLI` (4,000), the game fills it at its aspect with sharp bilinear (owner, 2026-11-16), with no fitted notice. Under 4,000, with `panel_scale = integer`, or with scanlines on a panel (`panel_scanlines`, from `display.scanlines = on`: the renderer draws scanlines only at a whole scale), it takes the largest whole vertical multiple. A fill whose height is a whole multiple takes the whole path. The scale rounds down. Each listed mode is a proposal. Order: whole vertical scale first, then the preferred size (the first listed mode), then the rate per game frame nearest the game's, then the list order.

### Readings of the Definition

Where the Definition allows two readings, the policy takes the one below. Each is one named constant or function; change only the named item. Items marked *owner* are product choices. The rules above already hold these owner decisions: pixel exact first with the fit last and always with `Notice::fitted`; any border height, standard heights first (OP-046 point 2); the crop bound of 8 lines per edge; "matches to two decimals" as under 5 mHz (`REFRESH_MATCH_MHZ`); padded below 75 % (`PADDED_FILL_MIN_PERCENT`).

- "Falls through the ones below" for `3x` and `4x`: the smaller multiples first, never the native rung (`walk_ladder`).
- *Owner (OP-046 point 1):* `native` means the game's lines 1:1, never a multiple; `auto` takes the best exact result for the monitor (`walk_ladder`, `crt_plan`). On 31 kHz `auto` is 2x and `native` is double refresh or the padded native mode.
- `native` with `exact` takes double refresh (`NativeDouble`) when the lines do not fit at the game's rate without padding. The Definition lists "Native, double refresh" as `native` with `exact_x2`, but also says each style runs at the game's exact rate or exactly twice it, and double refresh keeps the speed. The notice (`double_refresh`) tells the player.
- "Never show something the user did not choose with no notice": a style that falls to another rung sets `style_fallback`, and the menus decline that option with its reason (`picture_choices`).
- Border heights against the sources table ("a 224 or 240-line mode", "480p fit on 31 kHz" for a medium-resolution board): a 384-line board gets its own lines centred, not a fit (`border_lines`). System 24 (57.524 Hz) on `pc_31_120` is 384 lines in 512, of 528 picture lines (72.7 %, padded); on `arcade_31` 384 in 501 (76.6 %, not padded). The 384-line board at 55 Hz is 384 in 512 on `arcade_31`, of 526 picture lines (73.0 %, padded).
- "The smallest height in range that holds the picture" is at least `forced_picture_lines`.
- Border against padding: among the exact placements at one target, the ones that fill at least 75 % come first in ladder order, then the padded ones, the fuller first (`crt_plan`). A ZX Spectrum on `pc_31_120` at 50.08 Hz gets 2x (384 lines in 448, 63 % of 609 picture lines) before native (192 in 512, 31 %).
- *Owner:* a medium-resolution board (384 lines) on 15 kHz gets rung 3, interlaced 1:1 with borders, where its lines fill the field ("interlaced fit" in the sources table); the fit stays the fallback.
- *Owner:* `force_60` is 60.000 Hz and `force_50` is 50.000 Hz (`FORCE_60_MHZ`, `FORCE_50_MHZ`).
- *Owner:* a flat panel gets no notice for a small change of its rate (`notice`): the game and its audio run at the panel's flip rate over `repeat`. The status of `neptron-video` shows a speed change beyond `PANEL_SPEED_SILENT_PPM`; the notice shows it only above `PANEL_SPEED_NOTICE_MIN_PPM` (5 %). Each bound uses one comparison, `speed_beyond`, in ppm of the shown rate.
- *Owner, 2026-11-19:* one alert threshold for a speed change on every display class, `SPEED_ALERT_MIN_PPM` (5000 ppm of the shown rate, 0.5 %, the bound of the audio rate control). `speed_alert` is the one rule for the notice and for the status line of `neptron-video`. `TV_SPEED_SILENT_PPM` is this constant.
- "When the lines only fit that way" (rung 3): the lines do not fit a progressive range at the target rate, that is the line limit or `floor(h_max / rate)` less the vertical blanking (`progressive_capacity`). A short game is centred in the interlaced minimum.
- A width strategy below the GPU floor is replaced, not left without a mode. The dynamic super width needs a pixel clock of at least the floor, the bound of the validator; Switchres doubles while the clock is at most the floor.

### TV profiles

A TV profile (`MonitorKind::Tv { standard }`) has the fixed mode table of its standard: 240p and 480i on the 525-line standards, 288p and 576i on the 625-line standards (`TvStandard::modes`, ADR 0012). The policy does not call Switchres for it. It returns the same `Plan`, `Considered`, `Proposal`, `Placement` and `Timing`, so `choose`, `switch_for`, `notice` and `offer` work unchanged. Every proposal is one of the two table modes of the standard, so `neptron_safety::validate` accepts it.

**The rungs**, in order (`policy/tv.rs`):

| Rung | When | Example |
| --- | --- | --- |
| Native, progressive | A progressive game with at most 240 lines (525) or 288 lines (625): its lines 1:1, centred with black lines | SNES 256x224 on NTSC: 240p, 224 lines at line 8 |
| Native, progressive, cropped | A progressive game with up to 16 lines more: `OVERSCAN_CROP_MAX_LINES_PER_EDGE` (8) source lines hidden per edge. The uncropped entry stays with `Dropped::TvLines` | A 384x256 board on NTSC: 240p, 8 lines hidden per edge |
| Interlaced 1:1 | A progressive game too tall for the crop, up to 480 or 576 lines: lines 1:1, centred. For an interlaced game this is rung 1 (`Native`), and rung 3 drops with `SameAsNative`. A game that fits the progressive mode drops this rung with `FitsProgressive`, so a 240-line game is never doubled into 480i | VGA 640x480 on NTSC: 480i, 480 lines; SNES 512x448i: 480i at line 16 |
| Fitted | Always, last: the game scaled into the progressive mode with sharp bilinear, with the notice `fitted` | A 640x600 game on NTSC: 240p, 600 lines into 240 |

- A game too tall for a mode drops that rung with `Dropped::TvLines`. A GPU without interlace drops the interlaced rung with `NoInterlace`.
- **Picture modes.** `auto` and `native` walk the rungs above. `2x`, `3x` and `4x` have no mode on a TV: each multiple drops with `Dropped::TvNoMultiple`, then the walk goes on as for `native`. `offer` declines the multiples, and the notice sets `style_fallback`.
- **Refresh.** The only target is the field rate of the mode (`RefreshKind::Tv`). `exact_x2`, `force_50` and `force_60` go to `Plan::skipped`. A game nearer half the field rate than the field rate shows each frame twice (`repeat` 2).
- **Speed.** The game runs at the field rate, one frame per flip, and the session sets the audio run rate to the field rate read back. `Timing::changes_speed` is only the alert threshold: true when the game rate and the field rate differ by more than `TV_SPEED_SILENT_PPM` (5000 ppm of the field rate, equal to `neptron_audio::MAX_RATE_DEVIATION_PPM`). Above it `notice` sets `game_mhz` and `shown_mhz`, and the status shows `[!] speed (X to Y Hz)`. A 50 Hz game on a 60 Hz standard, or the reverse, gets its mode with the alert.
- **Placement.** The game's lines are 1:1 on every rung except the fit. In an interlaced mode the centred offset rounds down to an even line, so line 0 of an interlaced source stays in the first field. The width follows `tv_width` (below), centred in the 720 samples. The filter is nearest when the width is a whole factor of the game width, else sharp bilinear. `Proposal::horizontal` and `Plan::horizontal` are `None`. `source_index` is the index in `TvStandard::modes` (0 progressive, 1 interlaced).
- **UI.** The 320x240 UI canvas sits at whole factors, centred, with nearest: 640x240 at (40, 0) on 240p, 640x240 at (40, 24) on 288p, 640x480 at (40, 0) on 480i, 640x480 at (40, 48) on 576i. 2x is the largest factor inside the 704 safe samples. The vertical overscan margin is the UI theme's own safe area; how many lines a TV hides is a hardware check.
- **Overscan.** The game is placed as a console placed it, with no margin of its own. The kernel margin properties stay 0 (the KMS backend sets them).

**The width rule** (`display.tv_width`, `TvWidth`). Every mode has 720 samples at 13.5 MHz, and a 4:3 picture is 704 of them (`TV_SAFE_WIDTH_SAMPLES`). 704 samples over the 240 lines of a 525-line field (`TV_525_PICTURE_LINES`) give 2.2 samples per line of aspect 1 (pixel aspect 10/11); over 288 lines (`TV_625_PICTURE_LINES`) 1.8333 (12/11). The display aspect comes from `SourceGeometry::aspect_milli`; 0 means square pixels of the frame.

- `aspect` (the default):
  - A 4:3 source with 224 to 240 lines per field (`TV_CONSOLE_LINES_MIN` to `TV_525_PICTURE_LINES`) is a console picture and gets the width the hardware drew: `TV_525_CONSOLE_WIDTH_SAMPLES` (644: 256 pixels at 21.477 MHz / 4, 320 at 53.693 MHz / 8 and 512 at 10.739 MHz are each 47.68 us) or `TV_625_CONSOLE_WIDTH_SAMPLES` (650: the NES PAL draws 256 pixels at 26.602 MHz / 5).
  - A 4:3 source of more than 240 lines per field gets the larger of the console width and the aspect width, at most 704, so the width never falls as the lines rise (on 625 lines, 241 lines give 650 samples, where the aspect width alone is 589).
  - Every other source keeps its aspect: `aspect x lines x 2.2` on 525 lines, `aspect x lines x 1.8333` on 625 lines. The lines are the lines per field as placed: half the frame for an interlaced mode, the active lines for the fit. An overscan crop does not change the width.
  - A whole or half factor (1.5, 2.5, 3.5) of the game width within `TV_WHOLE_FACTOR_TOLERANCE_PERCENT` (3 %) of that width, a whole number of samples, and at most 704, wins. A whole factor takes nearest; a half factor and any other width take sharp bilinear.
  - An arcade source (`PolicySettings::arcade`) fills its monitor: the aspect width over its lines per field, at most 704, snapped as above (`board_samples`), not the console width. A 304x224 board is 657 samples on NTSC and 547 on PAL. A source taller than the progressive mode and its crop gets the fit into the interlaced mode first, on a GPU that sends interlace.
- `integer`: the largest whole factor of the game width at most 704 samples, with nearest. A game wider than 704 gets 704, scaled down. It ignores the shape: a 160-wide handheld becomes 640 wide.
- `fill`: 704 samples.

The widths in samples, for a 4:3 game of 224 lines:

| Game width | `aspect`, NTSC | `aspect`, PAL | `integer` | `fill` |
| --- | --- | --- | --- | --- |
| 256 (NES, SNES, Mega Drive H32) | 640, 2.5x, sharp bilinear | 640, 2.5x, sharp bilinear | 512, 2x, nearest | 704, 2.75x, sharp bilinear |
| 320 (Mega Drive H40) | 640, 2x, nearest | 640, 2x, nearest | 640, 2x, nearest | 704, 2.2x, sharp bilinear |
| 512 (SNES high resolution) | 644, 1.26x, sharp bilinear | 650, 1.27x, sharp bilinear | 512, 1x, nearest | 704, 1.375x, sharp bilinear |
| 640 (480i sources) | 640, 1x, nearest | 640, 1x, nearest | 640, 1x, nearest | 704, 1.1x, sharp bilinear |

Other aspects, `aspect`, sharp bilinear: Game Boy 160x144 (10:9) 352 NTSC, 293 PAL; Game Boy Advance 240x160 (3:2) 528 and 440; a 224x256 board turned upright (3:4) 422 (8 lines cropped per edge) and 352.

The Neo Geo draws 320 pixels at 6.000 MHz, 720 samples. Its core gives 4:3 at 224 lines, so it gets the console width, 640 samples, 11 % narrower. A per-system picture width would correct it (OP-099).

**The rates.** The field rates are exact millihertz from the table modes (`Modeline::field_rate_mhz`): 240p 60 054, 288p 50 080, 480i 59 940, 576i 50 000. The difference is in ppm of the field rate; an alert shows above 5000 ppm. Every 60 Hz console in the test table is silent on NTSC except CPS1 (+6 944) and the Neo Geo (+14 454); on PAL only the 50 Hz NES and SNES are silent (+1 458), and the Mega Drive PAL shows the alert (+7 568, 0.76 % fast). `every_console_of_the_spec_gets_its_mode_and_its_speed_result` in `tests/integration/policy_tv.rs` holds the mode, the ppm and the alert of each console on NTSC and PAL.

### What the engine does

1. Apply the EDID pixel clock limit to the GPU caps first (`EdidProfile::limit_caps`, OP-013).
2. On launch and on each geometry change, call `decide`, then `choose` with `|m| neptron_safety::validate(m, profile, caps)`. The policy does not depend on `neptron-safety` (the dependency rules forbid it), so the engine validates every proposal; a refused proposal is skipped, never set. Commit `token.mode()` of the winner, never `proposal.mode`: only the token is the mode the validator approved.
3. Call `switch_for` with the current mode. `ScaleOnly`: change only crop, destination and filter. `Modeset`: commit after the debounce.
4. Build each `Scene` from the winner's `Placement`, with its crop (a part of the frame, not a frame of another size). Run the core one frame per `Timing::repeat()` flips. The game runs at the read-back field rate over `repeat`, and the session sets the audio run rate to it; the audio rate control only corrects clock drift. `Timing::changes_speed()` only decides the speed alert.
5. Show `notice` in the quick menu. A `Notice` holds flags and numbers only, no text. The UI builds its "why" text from the plan: the `Dropped` reason or `Padding` of each `Considered` before the winner, `Choice::refused`, and `Plan::skipped`. It logs each `Considered` with its `Display` line.
6. Cache the plan by source geometry and settings. A decision takes tens of microseconds in the dev profile, but a cache keeps the Switchres lock off the frame thread for a repeated geometry.

### Known limits

- A monitor aspect other than 4:3 in the Switchres settings makes Switchres widen every mode by the ratio of the aspects (256 becomes 341 at 16:9). Every exact rung then drops with `WidthChanged`, and the fit wins. The policy could pass 4:3 to Switchres and keep the aspect for the border width only; that is an open question for the owner.
- A CRT profile on a GPU with a fixed pixel clock (`pi_vc4_composite`, 13.5 MHz) gets no mode: Switchres does not calculate for a fixed clock. That output takes a TV profile.
- At the crop bound, an overscan crop can hide real game content: arcade boards draw to the edge, and a vertical game shown unrotated loses columns of its upright picture (Donkey Kong on `arcade_15` loses 5 columns at each side). The bound is not checked against real game pictures.
- Some `auto` results stay small after the crop, because no whole multiple fits within 8 lines per edge, and the fit is the last resort. Fill is the game's share of the picture lines:
  - Vertical arcade games, not turned upright on a horizontal screen: Pac-Man on `pc_31_120` 288 of 501 (57.4 %), on `arcade_31` 288 of 474 (60.7 %); Donkey Kong on `arcade_31` 256 of 474 (54.0 %); both on `generic_15` and `arcade_15`, interlaced 1:1, 144 or 128 lines per field of 238 (60.5 % and 53.7 %).
  - Handhelds on 15 kHz, centred in 224 lines: Game Boy 144 of 242 (59.5 %); Game Gear 144 of 241 (59.7 %); WonderSwan 144 of 221 on `generic_15` (65.1 %); Game Boy Advance 160 of 242 (66.1 %).
  - 50 Hz computers on 31 kHz: ZX Spectrum at 2x, 384 of 609 on `pc_31_120` (63.0 %) and 384 of 582 on `arcade_31` (65.9 %); C64 PAL at 2x, 400 of 609 (65.6 %) and 400 of 582 (68.7 %).

### Rotation

The policy swaps the axes of a turned game, keeps the shape of the upright picture, and returns the crop in frame pixels. `Scene::rotation` turns the picture (ADR 0015).

## What the solver does

- It accepts a CRT profile with 1 to 10 ranges. A flat-panel profile is an error (it lists its modes), and so is a TV profile (`ModelineError::Tv`).
- A range that Switchres refuses, or whose blanking is outside the limits of `neptron-switchres-sys`, is an error with the index of the range and the values in nanoseconds. Every shipped preset passes.
- It returns at most one candidate per range, best first, in the order of Switchres. The first is the mode that Switchres selects. An empty list means that no range can show the source.
- From `GpuCaps`, Switchres uses only `pclock_min_hz` (its `dotclock_min`) and `interlace`. The safety validator judges the rest.
- A rotation of 90 or 270 degrees sets the "rotated" flag of Switchres. Switchres takes every source as 4:3, so `aspect_milli` is not used.
- The source refresh reaches Switchres as a `float`, as `display_manager::get_mode` takes it.

`Settings::default()` holds the defaults of `switchres_manager`, except doublescan:

| Setting | Default | Switchres default |
| --- | --- | --- |
| `doublescan` | off | on |
| `refresh_tolerance_mhz` | 2,000 | 2.0 Hz |
| `super_width` | 2,560 | 2560 |
| `monitor_aspect` | 4:3, from 1:4 to 4:1 | 4.0/3.0 |

Doublescan is off because not every DRM driver accepts a doublescan mode. The fixed values are the Switchres defaults: pixel precision on, interlace not forced to even, proportional scale on, vertical shift correction off, no geometry adjustment.

`src/convert.rs` is the one place where integers become Switchres doubles and back. Into Switchres: each integer becomes an `f64` without loss, then one division by a power of ten gives the unit of `switchres.ini` (Hz, µs, ms), so a profile from `data/monitors` reaches Switchres bit for bit as the preset text does. Out of Switchres: each timing is checked against its field (`u16`, `u32` for the pixel clock); the pixel clock is whole hertz (Switchres truncates it); a score is multiplied by 1,000 and rounded half away from zero. A value that does not fit is a `ConvertError` with the field, the value and the limit.

## The golden list

The expected modelines are recorded from Switchres at the vendored commit. No source independent of Switchres gives them. Each one is the output of the upstream standalone program, built from the same commit and not from this crate. That program reads the presets from its own table and selects the mode in its own `get_mode`, so a match also checks the shim and the conversion. The source geometries and where they come from are in the file.

To check a value against the standalone program:

1. Get the Switchres archive of the vendored commit (`vendor/switchres/README.md` has the URL) and unpack it into a new directory.
2. Build the program there: `c++ -std=c++11 -ffp-contract=off -I. switchres_main.cpp switchres.cpp display.cpp custom_video.cpp monitor.cpp modeline.cpp log.cpp edid.cpp -o switchres`. On Linux, add `display_linux.cpp`.
3. Run it from an empty directory with the command line in the comment of the case. The program reads a `switchres.ini` from the working directory and from `/etc` (or `./ini`) if one exists, and that changes the result.
4. `expect` is the timing part of the "Modeline" line, after the quoted label, with the spaces collapsed.

A changed modeline is a change in what NEPTRON sends to a CRT. Update the file only after the standalone program gives the same value.
