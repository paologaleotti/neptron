# neptron-gfx

Renderers for a `Scene`. `ReferenceRenderer` (CPU, pure Rust) defines the correct pixels. `GlesRenderer` (EGL, OpenGL ES 2) must match it.

## Public API sketch

- `struct ReferenceRenderer` with `render(&mut self, &Scene, &mut OutputBuffer) -> Result<(), RenderError>`
- `struct OutputBuffer { data: &mut [u8], width: u32, height: u32, pitch: usize }`, owned by the caller
- `enum RenderError`, with `Image`, `RectKind` and `MAX_RECT_SIDE_PX`. `ScanlineStrengthTooHigh` refuses a scanline strength above 100 %.
- `gles::GlesRenderer` (feature `gles`) with `headless() -> Result<Self, GlesError>`, `on_gbm(Rc<dyn GbmTarget>) -> Result<Self, GlesError>`, `pbuffer(width, height)` and `read_window(&mut OutputBuffer)` for checks of the window path, `render(&mut self, &Scene, &mut OutputBuffer) -> Result<(), GlesError>`, `draw_to_window(&mut self, &Scene, width, height) -> Result<(), GlesError>`, `gl_strings()`, `max_texture_side()` and `max_output_side()`
- `gles::GlesError`, `gles::MAX_AXIS_PRODUCT`, `gles::GbmTarget` (an unsafe trait: the GBM device and surface pointers)

## Reference renderer

The doc comment of `ReferenceRenderer` states every pixel rule. In short:

- Output: XRGB8888 as DRM defines it, little-endian, X byte `0xFF`. Every pixel of the output area is written. Row padding is not written. A pixel that shows nothing is black.
- Sources: XRGB8888, RGB565 and XRGB1555, native-endian. A 5-bit or 6-bit channel `v` becomes `round(v * 255 / max)`. X bits are ignored.
- Mapping: destination pixel `i` samples the source at `crop.x + (i + 1/2) * crop.w / dest.w`, an exact fraction. Each axis scales on its own. A sample outside the frame is black. A zero-size crop or destination shows no game.
- Nearest: the source pixel under the sample point. A point on an edge takes the right or the lower pixel.
- Sharp bilinear: the libretro `sharp-bilinear` formula with an integer prescale per axis. Taps clamp to the crop inside the frame. Each channel is the exact blend, rounded half up. At an integer scale it equals nearest.
- Turn: `scene.rotation` turns the cropped picture counter-clockwise before the scale, with the pixel rule in the doc comment of `Scene::rotation` (ADR 0015). Every other rule applies to the turned picture `T`: for `R90` and `R270` its columns are the lines of the crop. An axis that runs against its frame axis is the crop of the mirrored frame axis (`reference/turn.rs`), so the axis maps, the test for a sample outside the frame and the clamp of the far tap need no change. A turn is a permutation of pixels: it adds no rounding. The UI canvas is never turned.
- Scanlines: `scene.scanlines` darkens lines of the game picture, with the rule in the doc comment of `neptron_types::Scanlines` (ADR 0006). Only at a whole vertical scale `k = dest.h / T.h` of at least 2, where `T.h` is `crop.w` for `R90` and `R270`: the dark lines stay horizontal on the screen. Destination line `j`, counted from `dest.y`, is dark when `j mod k >= k - d`, with `d = ScanlineKind::dark_lines(k)`: for black lines the last `floor(k / 2)` lines of each group (2x: 1 of 2, 3x: 1 of 3, 4x: 2 of 4). A dark channel is the exact value times `(100 - strength) / 100`, rounded half up, on the gamma-encoded 8-bit values: `(c * (100 - strength) + 50) / 100` for nearest, and the exact blend scaled before its one rounding for sharp bilinear. Borders, samples outside the frame and the UI canvas do not change. A fractional scale or a scale of 1 shows no scanlines, and `Scanlines::NONE` gives the output of a renderer with no scanline support.
- UI canvas: opaque, over the game. The whole canvas scales to `scene.ui_dest` with nearest scaling, each axis on its own, with the sample rule of the game (pixel centres, `floor`). A part outside the output is clipped. A zero-size `ui_dest` shows no UI. The renderer does not choose the rectangle: the video side sets it with `ui_dest_fill` (CRT) or `ui_dest_uniform` (flat panel) from `neptron-types`.
- Rectangles: a crop, destination or UI destination side above `MAX_RECT_SIDE_PX` (65 536) is refused with `RenderError::RectTooLarge`, so no position or size can make the renderer panic.
- Integer maths only, so every host gives the same bytes.
- No `unsafe`: the module carries `#[forbid(unsafe_code)]`.
- Allocation: two small tables of sample positions grow on the first call and on a larger output. Other calls allocate nothing.

## GLES renderer

`GlesRenderer` (feature `gles`) draws a `Scene` with EGL 1.5 and OpenGL ES 2. It must give the pixels of the reference renderer. The doc comment of `GlesRenderer` states the rules. In short:

- Two quads: the game frame into `dest`, then the UI canvas into `ui_dest`, over black. The UI quad has the whole canvas as the crop and nearest scaling.
- One fragment source, built once for each pair of axes that blend (four programs). An axis blends only with sharp bilinear at a scale that is not a whole number: at a whole scale its weight is always 0, so it reads one tap, and sharp bilinear at a whole scale on both axes uses the nearest program. `BLEND_X` and `BLEND_Y` are preprocessor constants, not uniforms: the `vc4` compiler of the Raspberry Pi 3 turns a branch on a uniform into a select, so a single program read all four taps for every pixel.
- Each source image is a texture of `BGRA_EXT` bytes (`GL_EXT_texture_format_BGRA8888`, which Mesa has on every driver; `headless` and `on_gbm` give `GlesError::MissingExtension` without it), one texel per pixel, so the texture unit reads the pixels and the shader has no decoder. `XRGB8888` with packed rows goes to GL as it is: as a little-endian `u32` it is the bytes B, G, R, X. `RGB565` and `XRGB1555` are expanded to 8 bits per channel on upload, in a buffer of the renderer, with integer steps that equal the expansion of the reference for every value (a unit test checks all 65 536). A texture in the GL format of the pixel format (`UNSIGNED_SHORT_5_6_5`) would need no expansion, but the texture unit of `vc4` expands a 5-bit or 6-bit channel by bit replication, which differs by 1 from the `round(v * 255 / 31)` that GL and the reference define for 23 200 of the 65 536 `RGB565` values (`gles_compare` on the Pi). On the Pi the expansion of a 256x224 frame takes about 0.5 ms in the bench build of `cargo xtask os push`, and its upload about 0.5 ms. The loops index the slices: that build (incremental, no LTO) does not inline the iterator adapters of `core`, and a loop with them took 3 ms. `XRGB8888` rows with a pitch above the row are packed in the same buffer, so one `glTexSubImage2D` call uploads each image. Native byte order must be little-endian; a big-endian build stops with a compile error.
- The fragment shader computes the taps of each output pixel from its destination index with the integer rules of `AxisMap::tap`: the sample position as an exact quotient and remainder, the prescale, the weight, and the far tap clamped to the crop inside the frame. It reads each tap with one `NEAREST` texture read and blends them itself: two reads for one axis that blends (a SNES or NES picture from 256 to 640 columns), four for two. It needs `highp` floats. Every value is an integer below 2^24, so a 32-bit float holds it exactly, and each division is corrected to the exact quotient. The destination index comes from a varying of the vertex stage, half a pixel from any edge at a pixel centre, so `floor` gives it exactly. It does not come from `gl_FragCoord`: `vc4` gives `gl_FragCoord` at the pixel corner, and Mesa turns its y upside down for a window-system framebuffer and not for a framebuffer object, so a row taken from it was right in one of the two and one line off in the other.
- Turn: the quad and its uniforms (`u_crop`, `u_axis`, `u_bounds`) are on the axes of the turned picture, from the same `Turn` as the reference. The uniform `u_turn` gives each axis an integer offset and a sign (`frame_len - 1` and -1 for an axis that runs backward), and `u_swap` swaps the two axes for `R90` and `R270`; the shader applies them to each tap before its texture read. All values are integers below 2^16, so the turn is exact. No extra pass, and the texture is not turned. `MAX_AXIS_PRODUCT` applies to the axes of the turned picture.
- The game quad covers only the output pixels whose near source pixel is inside the frame (`AxisMap::inside`, the code of the reference), so the shader has no test for a sample outside the frame: the clear leaves those pixels black.
- The `LINEAR` filter of the texture unit, at the sample point of the libretro `sharp-bilinear` shader, would need one texture read per pixel. On the Raspberry Pi 3 it does not meet the tolerance: `gles_compare` there found sharp bilinear pixels up to 5 off with the sample point computed exactly from `gl_FragCoord`, and up to 37 off with the sample point as an interpolated varying, because `vc4` computes the texture coordinate and the filter weights in fixed point. Under softpipe both forms pass.
- `MAX_AXIS_PRODUCT` (2^23): on each axis the source side times the destination side must not be above it, or `render` returns `GlesError::ScaleTooLarge`. 320 to 1920 is 614 400; 2048 to 4096 is the limit. The reference has no such limit.
- Scanlines: the renderer takes the pattern of dark lines (period, first dark line, kept percent) from the code of the reference and passes it to the shader as the uniform `u_scan`, with a period of 0 for none. The UI quad never has a pattern. The shader finds the line in its period from the destination line, with the exact `divmod`. A nearest pixel on a dark line becomes `(c * keep + 50) / 100` with an exact quotient, so it equals the reference. A blended pixel scales the float blend before its one rounding, as the reference does in exact maths, so it can differ by 1.
- Nearest output equals the reference byte for byte. A sharp bilinear blend is rounded half up in the shader, in floats; a blend whose exact value is within float error of a half can round the other way, so a channel can differ by 1. `gles_compare` also passes on the Raspberry Pi 3 (`VC4 V3D 2.1`, Mesa 26.1.8), through the framebuffer object and through the window path, except the two axis product cases, whose 4096-pixel output is above the 2048 limit of `vc4`.
- `headless()` checks with `glGetShaderPrecisionFormat` that a highp float of the fragment shader has at least 23 bits of precision, as an IEEE 32-bit float has. GLSL ES 1.00 only promises 16 bits. Less gives `GlesError::LowPrecision`. It also checks `GL_VERSION` before the GL loader reads it, because `glow` panics on a missing or unknown version string (`GlesError::GlVersion`).
- `render` clears old GL error flags first, so a check reports only the call it follows.
- `render` checks the scene with the checks of the reference first, so it refuses the same scenes with `GlesError::Scene`, and leaves the output unchanged after an error.
- Target: `headless()` makes a context on the Mesa surfaceless platform (`EGL_PLATFORM_SURFACELESS_MESA`) with no surface, draws into a framebuffer object and reads it back with `glReadPixels`. `on_gbm(target)` makes a context on the GBM platform (`EGL_PLATFORM_GBM_KHR`) with a window surface on the GBM surface that `neptron-kms` owns; it gets the two pointers through the unsafe trait `GbmTarget`, so no GBM type enters this crate, and it holds the `Rc` until it drops. `draw_to_window(scene, width, height)` draws a `width` by `height` output at the GL origin of the window surface and swaps. `render` and `draw_to_window` go through one private `draw` function (checks, scanline pattern, size limits, the two quads); only the target binding and the finish step differ (read back, or swap). A window surface stores the last GL row first, so the picture is in the last `height` rows of the GBM buffer; the KMS backend shows those rows. The draw code does not depend on the target: GL rows count from the bottom, and the shader maps output rows from the top. `GlesError::NoWindow` is the error of a window draw on a renderer with no window.
- EGL is loaded at run time from `libEGL.so.1` (`khronos-egl` with `dynamic`), and every GL function through `eglGetProcAddress` (`glow`). No build links EGL or GL, so `cargo xtask clippy -p neptron-gfx --features gles` and the unit tests of the module run on macOS too. The pure modules of `gles` (texels, quads, shaders, the version check, the error type, the UI row copy and the cover of the game) also build in the tests of the default build, so `cargo xtask test -p neptron-gfx` and tier 1 run their unit tests; only `ffi` and `renderer` need the feature.
- Threads: the renderer is not `Send`. Each call makes its context current first, which replaces any other context that is current on the thread. Dropping the renderer releases the current context of the thread.
- All surfaceless renderers of a process share one EGL display. With `EGL_KHR_display_reference` each renderer holds a counted reference, and dropping one leaves the others working. Without it a renderer never calls `eglTerminate`, so dropping one renderer cannot break another, and the display stays initialized until the process ends. Mesa 26.1 does not have the extension, so the guest takes the second path.
- Allocation: the textures, the buffer of source texels, the framebuffer and the read-back buffer are made on the first call. A source texture and the buffer of source texels only grow: a frame smaller than the storage goes to its top left, and the uniform `u_frame` gives the shader the size of the storage. So a game that switches between sizes (a SNES hi-res or interlaced frame, the two widths of the Mega Drive) allocates once, at the first frame of its largest size; the renderer does not know the core's maximum geometry, which only the session has, and the `Display` contract does not pass it. The framebuffer and the read-back buffer are made again when the output size changes. Other calls allocate nothing.
- The game under the UI: the UI canvas is opaque and comes last, so the game quad is drawn only in the parts of its area outside the UI quad (at most four scissor rectangles: above, below, left and right of it), and not at all, with no upload, when the UI covers it (`game_uploads()` and `game_parts_drawn()` count what goes to the GPU). The pixels do not change. On the Pi 3 a game with the keep or revert dialog over it took 4.9 ms of GPU time a frame (the game quad, 3.4 ms, then the whole UI quad); with the game drawn in the two side strips that the 640-column canvas leaves on a 720-column TV mode, it takes 2.2 ms.
- UI uploads: the UI texture keeps its canvas between calls, with a copy of its rows in the renderer. A call sends only the rows from the first to the last that differ from that copy, and a canvas with no change sends nothing; the game frame goes whole in every call. A menu or a dialog changes only on input or once a second, and the upload of the whole 320x240 canvas took about 0.6 ms a frame on the Raspberry Pi 3; the comparison of its rows costs less. `ui_rows_uploaded()` counts the rows sent. New storage, a canvas of another size or format, and a failed upload send the whole canvas at the next call.
- `unsafe` is only in `src/gles/ffi.rs`. Every other module of `gles` carries `#[forbid(unsafe_code)]`.

The check against the reference is `cargo xtask gles-compare` (tier T3). It builds `examples/gles_compare.rs` for the guest and runs it in QEMU, where Mesa softpipe gives software GL. It renders every golden scene and more scenes (every value of each pixel format, both filters on every format, crops, a 1920x240 super-width mode with and without the UI, a flat panel with the UI, 1080p, the axis product limit, a UI larger than the mode, an empty scene, frames and canvases with a zero side, crops wholly outside the frame, a 1x1 source, 1x1 destinations, destinations wholly off the mode, each turn (`R90`, `R180`, `R270`) with each pixel format, nearest, sharp bilinear, scanlines and a crop that reaches outside the frame, a 320x240 frame on its side shown upright at 3x on a 1080p panel with the UI over it and at 1:1 and 2x with scanlines, and black scanlines: 240p line-doubled to 480p, 224 lines in 480p with sharp bilinear, 3x, 4x, every RGB565 value, a destination above the mode, a fractional scale, the UI over the game) with both renderers. One more check runs every scanline strength from 0 to 100 % on every 8-bit channel value. It also checks the error paths (the reference checks, a scanline strength above 100 %, the axis limit, the axis limit on the axes of a turned picture, the texture and output limits read from GL at run time), that a second renderer can come and go while the first keeps drawing, that a UI canvas that changes in steps sends only the rows that changed and still equals the reference, and, through a new offscreen renderer and a new pbuffer renderer, that a game under the UI is drawn only in the parts the UI leaves (`game_uploads()` and `game_parts_drawn()`: none for a covered game, two for a UI in a corner, four for a UI in the middle rows) with the pixels of the reference. Two scenes put the UI over the game asymmetrically (a corner, and lines 40 to 199 of a 300-line output over a game at lines 0 to 239), so a scissor that counts rows from the wrong edge fails on both paths. Every scene up to 1920x1920 also goes through the window path: `GlesRenderer::pbuffer` draws with `draw_to_window` into an EGL pbuffer, a window-system framebuffer as the window surface on GBM is, and `read_window` reads it back. QEMU checks both paths on softpipe, which treats them alike; only a run of the program on the target GPU shows a driver that treats them apart (on the Pi 3 copy `target/gles-compare/gles_compare` there and run it). A nearest or UI pixel must be equal, a sharp bilinear game pixel within 1 per channel, and no row padding byte may change. The exit code is the number of failed checks.

## Goldens

`tests/goldens.rs` renders the scenes of `tests/common/scenes.rs` and compares them with `tests/goldens/*.ppm` byte for byte. The format is binary PPM: the header `P6\n<width> <height>\n255\n`, then 3 bytes (R, G, B) per pixel, rows top to bottom. Most image viewers open it. The output X byte is not in the file; the test checks it separately.

The `turn_*` goldens cover `R90` at 2x, with 2x scanlines and with a crop that reaches outside the frame (sharp bilinear), `R180` with a crop (RGB565), and `R270` with sharp bilinear on both axes (XRGB1555). The test pattern has red to the right and blue down, so each turn gives its own picture; the unit test `r90_shows_a_column_read_downward_as_a_line_read_left_to_right` pins the direction.

The `scanlines_*` goldens cover 2x at 0, 50 and 100 %, 3x, 4x, a fractional scale, a scale of 1, a crop with a destination on an odd line, the UI over the game, and sharp bilinear, with each pixel format once. The test `scanline_strength_sheet` also writes `target/tmp/scanline-sheet/scanlines_2x_strength_0_50_100.ppm`: one 256x224 picture at 2x with black scanlines at 0, 50 and 100 %, side by side, to look at. It checks each panel with the pixel rule.

When a golden does not match or is missing, the test writes the rendered image to `target/tmp/goldens-actual/<name>.ppm` and prints the difference. To accept a new image, look at it first, then copy it to `tests/goldens/`. Never copy an image to get a green run.

## Must never depend on

- `neptron-kms`, `neptron-video`, `neptron-ui`
- EGL or GL crates outside the `gles` feature

## Rules

- `unsafe` is allowed in this crate, in one module with a safe wrapper around it, for the GLES code only. Every `unsafe` block has a `// SAFETY:` comment.
- Features: `gles`. No feature is on by default.

## Status

The reference renderer is complete. `GlesRenderer` matches it under Mesa softpipe in the QEMU guest. On the Raspberry Pi 3 (`vc4`) the example `gles_compare`, copied to the Pi and run there by hand, passes too, except for the two cases above the output limit of `vc4`; no tier runs it there. The KMS target (EGL on GBM) is checked on `vkms` by `cargo xtask kms-check`: its writeback picture equals the reference renderer, and equals `render` of the same scene with scanlines on.
