# neptron

The frontend binary. It holds only wiring, no logic: it joins the library, the settings, the UI, the session, the ODREN engine and its guard, the input and the control protocol on one frame loop.

## Run it on a desktop

The window backend needs SDL3 (`brew install sdl3` on macOS, `libsdl3-dev` on Debian). From the root of the checkout, with a folder of ROMs and a state folder of your own:

```sh
mkdir -p /tmp/neptron/share/roms/nes /tmp/neptron/state /tmp/neptron/cores /tmp/neptron/run
cargo run -p neptron --features window -- --backend window \
  --share /tmp/neptron/share --state /tmp/neptron/state --data data \
  --cores /tmp/neptron/cores --run /tmp/neptron/run --no-control
```

- Put games in `share/roms/nes`, `share/roms/snes` or `share/roms/megadrive`, and the cores (`fceumm_libretro.dylib` named `fceumm_libretro.so`, and so on, as `data/cores` names them) in the cores folder.
- Keys: arrows, X accepts (RetroPad A), Z goes back (B), S is the menu button (X), Right Shift and Return held together for 0.5 s open the quick menu, and held for 5 s they are also the blind recovery.
- A launch, and the end of a game, end the process with exit code 75: one process holds one core. Run it under the launcher to get the next run at once: `cargo run -p neptron-launch -- --no-device -- target/debug/neptron --backend window ...`.

`cargo xtask clippy -p neptron --features window` checks the window build. The `kms` build compiles only on Linux.

## A run

One run is one process. It shows the game list, or it runs one game, because `neptron-libretro` allows one core per process and the display descriptor closes with the display. A run ends with an outcome:

| Outcome | Exit code | What the launcher does |
| --- | --- | --- |
| Relaunch: a launch from the list, the end of a game, a game that did not start | 75 (`RELAUNCH_EXIT_CODE`) | Starts the next run at once |
| Quit: the window was closed | 0 | Stops |
| Reboot: `Settings > System > Reboot`, confirmed (`Outcome::Reboot`) | 80 (`power::REBOOT_EXIT_CODE`) | With `--power`: asks init for a reboot |
| Power-off: `Settings > System > Shut down`, confirmed (`Outcome::PowerOff`) | 81 (`power::POWER_OFF_EXIT_CODE`) | With `--power`: asks init for a power-off |
| The run cannot start (`BootError`) | 1 | Starts it again after its backoff |

Before a relaunch the run writes `run/next.toml` (the relaunch file, `relaunch.rs`): the game to launch, or none for the list, a notice for the player, and the pad on each port of the input source (`pads`, `PadRecord`), so the next run keeps the order of the players. The next run takes and removes it. A game path must be relative, with no empty, `.` or `..` part, and the system a plain id (`GameRef::check`): the run joins it to the ROM folder. A file that fails the check is removed, and the start is a new boot to the game list. The run folder is a RAM file system (`/run/neptron` on the image), so a power cut leaves no file.

**A relaunch is not a new boot.** A run that starts from a relaunch file (a game, or the game list after a game) calls `Guard::continue_boot`: it never prompts and counts nothing. A new boot (`Guard::boot`) sets the run marker of the guard record; a good picture or a clean end of the run (`Shell::finish`: a relaunch, a quit, a reboot, a power-off) clears it. A crash, a hang or a power cut before a good picture leaves it set, and the next new boot counts one failed boot.

## Boot, before the first frame

The guard boots, and its record is written, before every step that can fail for a reason other than the display, so a start that fails later still counts. A sound device or a gamepad subsystem that does not open is a notice, and the run goes on with no sound or with keyboards only (`devices::MaybeSink`). The sound device opens once per process, before the first frame, through `devices::open_audio`: the device of `audio.output`; when that one is absent or does not open, the device that `auto` takes (the one HDMI or DisplayPort output with a monitor, else the first analog output, else the default device), then the first analog output, then the default device, with a notice at each step. With ALSA the list is read from `/proc/asound`, so HDMI and DisplayPort outputs are in it. The setting stays as it is. The log names the driver, the devices, the choice of `auto`, each device that failed with its error, and the device that opened (`docs/spec/audio-settings.md`). A game run follows a relaunch file, so the run before it counted the boot already.

First of all, before a backend reads a setting, `prestart::prepare` imports the first-boot file `neptron.toml` at the root of the boot partition (`/boot` on the image, `--boot DIR`; `boot_file.rs`, `docs/spec/raspberry-pi.md`), once per process. Then it reads `display.output` and `display.monitor` for the backend, and the backend reads `audio.output`, so the first start after a change of the file already opens the output and the sound device that the file names. `boot_file::decide` is pure: when the SHA-256 of the file differs from the one in `state/neptron.toml.sha256`, it gives the values that the schema accepts at the global level, and `boot_file::import` writes them into `global.toml` through `Storage::apply`, then stores the hash (temp file, fsync, rename). The same file at a later start changes nothing, so a menu change stands. Only the keys in the file are copied; the shipped files have every key commented out, so they copy nothing. An unknown key and a refused value are ignored and listed with their line. `display.pi_dac` is not in the schema: `none` is silent, another value gives a notice. A file that cannot be read, is larger than 64 KiB (`MAX_FILE_BYTES`), is not UTF-8 or does not parse changes nothing and keeps the stored hash, so each new boot lists it until it is fixed. A failed write of the settings is a notice, and the next start tries again. When the hash cannot be stored, each start copies the file again, so a menu change of a key that the file sets is lost at the next start; the notice says so. The import only writes settings: the backend and the steps below decide the display from them, as for a hand edit of `global.toml`, so a display value from the file passes the monitor checks, the guard and the safety validator.

Before all this, the KMS backend waits for a display when `display.output` is `auto` (`display_wait`). It reads the connectors in sysfs every 250 ms (`DISPLAY_POLL_NS`) for at most 15 s (`DISPLAY_WAIT_MAX_NS`) until one qualifies by `neptron_kms::choose` itself: connected, not a writeback connector, and not an analog connector with no EDID, which is used only when the settings name it. sysfs gives the type name of a connector, not its number, so `display_wait::connector_class` maps the name, and a test keeps it equal to `ConnectorClass::of_type` for every DRM type. DVI-I carries both signals, so for it the wait uses `ConnectorClass::of_connector` with the sysfs EDID, as the open does: a DVI-I panel is digital, a DVI-I CRT or a DVI-I with no EDID analog. A digital connector whose status reads `unknown` has had no probe yet and counts as ready; the forced probe of the display open decides. The app depends on `neptron-kms` with its default features for this rule, which compile no DRM code. A named output does not wait. The display open takes the launcher's descriptor and cannot be tried again, so the wait comes before it. When the open still finds no connected display, the frontend exits with code 69 (`NO_DISPLAY_EXIT_CODE`) before the guard record is written: the start counts as no failed boot, and the launcher starts it again after a short fixed wait, with no backoff. A stop request ends the wait, with its own log line.

The output rule of a Raspberry Pi (`docs/spec/raspberry-pi.md`, "The output rule"). A composite connector reports no display (`unknown`, no EDID), so the connector choice never takes it under `auto`. When a composite connector of a GPU whose capability table entry has the `tv_encoder` quirk exists (`display_wait::tv_fallback`), the wait is at most 3 s (`COMPOSITE_FALLBACK_WAIT_NS`, a first value that the bench sets), and a start that then finds no display that answers opens that connector by name (`display_wait::auto_output`). An HDMI display that answers in the wait wins, through the panel path. On a Pi 3 HDMI and composite share one pixel valve, so only one is driven. `display.output = "Composite-1"` gives composite with an HDMI display connected. Each look reads the limit again, so connectors that appear while the driver loads set it. The first run of a boot chooses the output once (`boot_output`): under `auto` it writes the connector it drives to `run/output`, and every relaunch of the boot (each game launch and each return to the game list) opens that connector by name, with no wait. So nothing switches between HDMI and composite while the frontend runs, also when an HDMI display starts to answer later. A relaunch whose connector sysfs no longer shows, or shows as `disconnected`, applies the rule again, with a log line. `display.output` wins over the kept connector. A start that is not a relaunch (a new boot, or a start after a crash) removes the file and applies the rule.

A TV output. The KMS backend reads the `TV mode` property of the connector in use (`KmsDisplay::tv_standards`) into `Runtime::tv_standards`. A connector with the property takes only the modes of a TV profile (ADR 0012), so the run decides every monitor from it: the wanted monitor is the profile of `display.tv` (`auto` is NTSC, `TV_SAFE_STANDARD`), and `display.monitor` has no effect, with a notice when it is not `auto`; the safe default, so also the boot prompt's revert, safe mode and the blind recovery, is the NTSC profile; a guard record gives back only the TV profile of a standard the connector offers. A preset file cannot take the id prefix `tv_` or the TV kind (`PresetError::Reserved`). A revert of the boot prompt writes `display.tv`, never a `tv_` id into `display.monitor`. The Display panel shows `TV standard` and `TV picture width` only on a TV, disables `Monitor profile` there (`Not used on a TV`), greys out the standards the connector does not offer, and names the standard on the mode line (`NTSC 240p 60.05 Hz`). Other outputs never name a standard. A connector whose `TV mode` property lists no standard that NEPTRON knows would refuse every mode: the KMS backend logs it and exits with `NO_DISPLAY_EXIT_CODE`, as for no display, and `Detected::safe` gives no profile for it (`MonitorError::NoTvStandard`). sysfs does not show the property, so such a connector is found only when it opens.

1. The problems and log lines of the import of `neptron.toml` (`Runtime::boot_file`, see below): notices on a new boot, log lines on a relaunch. A missing file is a log line only.
2. The settings: `global.toml`, and for a game its system and game files. A file that cannot be read is an empty layer and a notice.
3. The monitor presets from `data/monitors` at run time (OP-044): the binary embeds no GPL data. A bad file is left out with a notice.
4. The detected output from sysfs, for the connector the backend drives (`Runtime::output`) and its `subconnector` property (`Runtime::subconnector`, read by the KMS backend): the connected connectors, the profile of that connector's own EDID by its class, the GPU caps of the capability table. The class rule is in the `neptron-platform` README: an analog EDID, a `VGA` or `DVI-A` subconnector or an analog-only connector is a CRT; a digital EDID on a digital connector is a flat panel. The named connector uses only its own EDID, whatever its status (`connected`, `unknown` as a VGA output with no EDID often is, or `disconnected`); it never borrows the EDID of another display. A name that no connector has (the window, the fakes) gives no EDID. Only `auto`, which the KMS path uses before the display opens, takes the first connected display that gives a profile.
5. The flat-panel profile is cut to the modes that the display's caps and the panel limits (`PANEL_WIDTH_MAX_PX` 3840, `PANEL_HEIGHT_MAX_PX` 2160) allow. A panel whose native mode is above them starts in its largest listed mode that fits, with a notice that names both modes. A panel with no mode that fits gives no profile, with a notice.
6. The guard record from `state/video/guard.toml`. A record that cannot be read is the default record. The file keeps one last known good per place (`[[places]]`: the connector and the identity of the monitor on it). The guard gets the entry of this start's place only, so a profile confirmed on one connector never drives another display without a prompt, and a boot at another place never deletes an entry.
7. The safe default, with `auto` and `exact` (`SAFE_START_PROFILE`): the range profile of a CRT that gives EDID; a trusted flat panel (`Detected::trusts`: a digital link, the EDID of the driven connector, `display.monitor` `auto` or `flat`) in its native mode; else `generic_15`. So with no EDID, a broken EDID, a DAC whose EDID is digital, and a named preset on a panel, the safe start is `generic_15`. Without it the run cannot start.
8. `wanted`: the monitor of `display.monitor` (`auto` is the detected profile, a panel included, or `generic_15` with no EDID; `flat` is the flat-panel profile of the connector's EDID whatever its class, for an LCD with a VGA input; an unknown id, or `flat` with no listed mode, is the safe default with a notice) and the global picture mode and refresh rate.
9. The library cache. In the list, a scan starts on its own thread and replaces the index when it ends. The first scan thread of the process also reads the arcade index of the image (`/usr/share/neptron/arcade/fbneo.idx`, `Paths::arcade_index`) and the library keeps it (`ArcadeState`). A missing or damaged index never stops the boot: the arcade folders then list each zip by its file name. A clone whose parent is in the same list is folded: the parent's row gives `Other versions (N)`, and `Library::window` of `GameSource::Versions(id)` lists the parent and its clones, each titled with its details (`Star Patrol (Japan)`). A folded clone has its own game id, so it starts and comes back as any game.
10. The list: a `VideoEngine` for the menu source (320x240, 60 Hz, 4:3, `MENU_SOURCE`). A game: `Session::launch` with the resolved settings, the core options of `data/cores` (OP-055), `RunRateSource::ReadBack` on KMS and `Measured` in the window. A launch that fails ends the run with a relaunch to the list and the reason as a notice (`Booted::Relaunch`, with the log lines that the binary writes). A core that refuses the file (`LaunchError::Refused`) or stops during the load (`LaunchError::CoreStopped`) gets the notices S1 and S2 of `docs/spec/arcade.md` section 10.1, which quote the first error line of the core (`start_failure.rs`).
11. `Guard::boot` (a new boot) or `Guard::continue_boot` (a relaunch: no prompt, so a change that was not kept never reaches a later run, and no revert notice shows), with the trust of the display (a trusted, safe-default or kept monitor boots with no prompt), and the record it returns is written at once (temp file, fsync, rename) before the first modeset. When that write fails (a read-only or full state partition), the boot cannot count itself, so it could fail again and again and never reach safe mode: this start uses the safe default (`Guard::recover`, with a notice and no tone). In a game, `follow_settings` with the game's policy follows.

## One frame

Each frame reads the clock once and gives that time to every guard call, the hotkeys and the key repeat of the frame.

| Game list | Game |
| --- | --- |
| Poll the input once, ports, hotkeys. Blind recovery calls `Guard::recover` | The session polled the input in its last frame |
| Navigation from the events, with key repeat | Navigation from `Session::input_events`, only while the UI shows; else only the menu button after `menu_opened` |
| Screensaver: the idle timer (`shell/screensaver.rs`) | The same, from `Session::input_events`; `hide_picture` while it shows |
| Snapshot: confirm, display mode | Snapshot: confirm, session, `video_status` (the read back, never a proposal), display mode |
| `Screens::update`, then the intents | The same |
| `SceneCanvas::paint`: the canvas is drawn only when the scene changed | The same, while the UI shows |
| `begin_frame(MENU_SOURCE)`, `present(None, canvas)`, `wait_flip` | `run_frame(canvas or None)` |
| `Guard::tick`, also after a failed present | `Guard::tick` |
| No flip: the loop waits for itself one 60 Hz frame | `blanked`: the same |

- Key repeat (`nav.rs`): a direction repeats after 400 ms, then every 66 ms. On `PromptOpened` every repeat stops and every held key is ignored until its release (OP-048). A, B and X are accept, back and menu; Start and Select are left to the hotkeys.
- The screensaver (`docs/spec/screensaver.md`): `neptron_ui::screensaver::Idle` gets each frame the time, whether an input came (a press, a stick axis that leaves its dead zone, or an action of the navigator, so a held direction counts), and whether it may show: in the game list or in a paused game while the UI shows, with no confirm of the guard and no guided mapping. While it shows, `Snapshot::screensaver` holds the count of its UI frames and the router draws it. In the game list each step shows for the `repeat` flips of the menu mode, so double refresh does not double the speed; in a game the session repeats each frame itself. The input that wakes it is consumed: the actions of the frame are dropped and `Navigator::hold_back` ignores the held controls until their release. The hotkeys still see the input, so the blind recovery works under it. The time setting is read at boot and after each live change.
- The quick menu is never a toggle: the session ignores a second hotkey, and the app only opens it (OP-051). Resume, reset and quit go to the session.
- A notice at the first picture of a game that is not exact (`shell/picture.rs`): one sentence for each reason of the policy (`Notice::reasons`: a soft picture and its cause, a small picture, a speed change, double refresh), with the texts of `docs/spec/arcade.md` section 11; a fit or a crop with no reason of its own gives the words of the video status.
- The speed notices of a slow game (`speed_notice.rs`, `docs/spec/pacing-audio.md`): "This game runs at {p}% speed. This machine is too slow for it." when `Session::slow_speed_percent` first gives a value, and "Sound off: the game runs at less than half speed." at each turn of `Session::sound_too_slow` to true. The speed notice shows again only after the game was no longer slow, and at least `SLOW_NOTICE_GAP_NS` (60 s) after the one before. Both are Warning notices: they wait for the quick menu, as every notice in a game, and go to the log.
- The one-time notice of a vertical game: the first time a game turned by 90 or 270 degrees shows interlaced on a 15 kHz CRT or a TV with `display.vertical = exact`. The ids of the one-time notices shown already are in `state/config/notices.toml` (`notices.rs`, open point A4). The boot reads it with the settings; a missing or damaged file shows the notices again. The writer thread writes it whole (`Job::Notices`).
- The arcade rules of the policy (`PolicySettings::arcade`) for a game of a system whose core is the core of the arcade index (`library::runs_arcade_boards`): `GameContext::arcade`, which `Config::policy` reads.
- `FrameReport::ended` or any `SessionError` (`DisplayStalled` included): the game ends with `quit()`, and the run relaunches to the list, which opens the display again in a new process. This is the one rule for a display that stops. `EndReason::FailedStart` (the core stopped the game before it showed, or soon after an error line or a message at the launch, as FinalBurn Neo does at its own error screen) gives notice S2 and puts the error lines of the core in the log. `CoreShutdown` (a game that ran) gives notice S3 with the last message or error line of the core, so a stop by the core never returns in silence. `shell::intents::pick_notice` decides between the end notice and the notice of a lost save: S2 comes first, and a lost save comes before S3 and before a session error. The notice that loses goes to the log.

## Flat panels

- The panel starts in its native mode, so the panel does no scaling. The policy puts the game at the largest whole vertical factor at which its display aspect fits, centred, with black around it. The width follows the core's aspect, so it is often a fraction of the game width: the renderer then uses the sharp bilinear filter, which the video status shows as `sharp` and never as an alert. A 50 Hz game takes a listed 50 Hz mode of the native size.
- The menu is the 320x240 canvas at one whole scale, centred: 4x, 1280x960 at (320, 60) on 1080p.
- The display panel shows the panel's name and the mode it starts in as the detail of `auto` in the monitor row; `flat` shows the same for the panel profile.
- Scanlines follow `scanlines_for`: `auto` is off on a panel.

### The first boot on a panel

- A panel on a digital link whose EDID the driven connector reports, with `display.monitor` `auto` or `flat`, is trusted (ADR 0013): the boot shows its native mode with no prompt, and the panel is the safe default of the run, so a revert and the blind recovery show a picture.
- A named preset on such a display is not trusted: the boot prompt opens, and with no answer the guard goes to `generic_15`, the safe default of that run.

## Settings and the guard

| Setting | What a change does |
| --- | --- |
| Safety none: scanlines, scanline strength, the Start hold | Written at once (writer thread) and applied live |
| Picture mode, refresh rate, TV width, while the guard is `Confirmed` | Written at once and given to `Guard::follow_settings`: no prompt |
| Monitor, TV standard; or a picture mode, refresh rate or TV width in a pending change or in safe mode | Changed in memory and given to `Guard::propose`. Written only on `Confirmed`. Taken back on `Reverted` and `SafeMode` |
| Output (`display.output`) | Shown, not changed from the menu or the protocol; a new connector at the next start opens the boot prompt |

- `PromptOpened` puts the confirm dialog in the snapshot with the guard's deadline. `KeepMode` calls `confirm` with the open prompt; every refused confirmation goes to the log as `keep refused: <reason>`, and the dialog stays (for example a Keep while the change shows no valid picture). The dialog shows no Keep at 0 s, so a refusal for the deadline (`Expired`) only comes from a fault. `RevertMode` calls `decline`.
- `Reverted { rewrite: Some(config) }`: the monitor, picture mode and refresh rate of that configuration go to the global settings, never `Guard::active()`.
- `SafeMode(Recovery)` plays a short tone: in the game list through the app's sink, in a game mixed into the next core frames by the session's audio pipeline (`Session::write_cue`), so the whole tone plays and adds no latency. The display panel shows "(safe mode)" after the mode while the guard is in safe mode, and the rows "Keep this picture" (`Guard::keep_shown`, then the safe default goes to the global settings) and, after failed boots, "Try my settings again" (`Guard::retry_settings`). The notice of a start in safe mode shows once per power cycle (`run/safe-notice-shown`), with no tone. A revert notice shows only when something on screen went back, and never for a superseded change.
- The picture mode and refresh rate options are the answers of `neptron_modeline::policy::picture_choices` for the pair that a pick stores: the option with the stored value of the other row. The app stores the two rows as one pair: every write sets both keys at one level in one write (`Config::write_pair`), and the Menu button on either row removes both. Plain: a pick stores the row with the stored value of the other row. With the reset of the other row: the tag "Rate to Auto too" (or "Mode to Auto too") in the row, and a pick stores the row with the other row at Auto, with the notice "Refresh rate is set to Auto too."; a revert restores both. Declined: the option is grey with its reason, for example "Not possible with this screen and video output" (the help line under the list reads "Not available. Not possible with this screen and video output."). The help line always keeps the option's own text. The quick menu judges the running game and shows the line rate and the field rate of the mode that each option gives. Settings > Display writes for every game: it judges with the global values for the running game and the reference sources (`REFERENCE_SOURCES`), shows no rate, and tags an option that some games cannot have "Not all games"; the notice after the pick says why. A write at a level is judged with the values resolved up to that level (`Config::policy_up_to`). The engine keeps the answers keyed by the request and the generation of its inputs (`VideoEngine::answers`), and the frame makes new ones at most `PICTURE_DECISIONS_PER_FRAME` (2) decisions at a time; while they are in work, the declined options keep their reasons, the offered ones show "..." in place of their rates or tags and take no pick, and the help line shows "...". The menus and the protocol pass the same gate (`pages::gate`): a greyed value is refused with "Not changed: {reason}." and changes nothing; the protocol sets one key, so it refuses a value that needs the other row at Auto, and says so. The keep prompt of the quick menu moves the pair of the game to the level it names, and the game level loses both keys in one write; the answers of the prompt are made over frames while the quick menu is open, and a button waits until its answers are there. A move that the level refuses, or a move to every game while the system holds its own pair, leaves the pair at the game level, with a notice.
- The display panel writes the global level; the quick menu writes the game level, and its keep prompt moves a change to the system or global level.
- A row whose setting does not apply to the display of the run (`applies_to` in the schema) is disabled with the reason `Not used on a flat panel`. The class is that of the monitor the guard gave the engine. On a flat panel this is the refresh rate.
- The audio panel (home, `Audio`) writes `audio.volume` and `audio.output` at the global level. The quick menu has a `Volume` row. A volume change reaches the running game at once (`Session::set_volume_percent`); in the game list it only reaches the file. A new output takes effect at the next run, which is a new process.
- The System panel (`Settings > System`, `pages::system_page`) holds `Reboot` and `Shut down`, each behind a confirm question with the focus on `Cancel`. A confirm ends the run as a quit (`Shell::finish` writes the queued settings and the guard record, the threads are joined, the display is left as after a quit: the last validated mode, held by the launcher) with `Outcome::Reboot` or `Outcome::PowerOff`, and the binary exits with code 80 or 81 (`end` in `main.rs`; `power::exit_code` gives the same codes to the tests). A reboot or a power-off is a clean end of the run, so it counts no failed boot (`Guard::close_run` in `Shell::finish`). The rows are enabled only in the game list and only when the launcher gave power control (`NEPTRON_POWER=1`, read into `Runtime::power` by the KMS backend; the window backend never has it). In a game the reason is `Not during a game`: the player quits the game first, so its save RAM is written by its own quit. With no power control the reason is `Needs the launcher`. When the launcher could not carry out the request of the run before, the next start gets `NEPTRON_POWER_FAILED`, and the KMS backend shows the Warning notice `The restart did not work.` or `The shut down did not work.` (`power::failed_notice`). The app checks the rules again when the action arrives (`power::takes_request`, `Shell::request_power`): the game list, power control, no display change waiting for its confirmation, and no outcome yet, so a second request in the same frame changes nothing.
- The format of the share partition (`storage::FormatOffer`, `Shell::request_share_format`). When `storage.toml` offers a format (`share_fix = "format"` with the device, start, size and type of partition 4, all well formed: `StorageStatus::format_offer`), the System panel gets a third row, `Format share` (`pages::FORMAT_SHARE`), behind a confirm question that names the size (`FormatOffer::size_text`, decimal units). With no offer the row is absent. It follows the rules of the other two rows (`power::takes_request`). On the confirm the writer thread writes `/state/share-format-request` (`Job::ShareFormatRequest`, `FormatOffer::request_text`, with `atomic::write`), and the run ends with `Outcome::Reboot` only when the writer thread gives back that the file is written (`Outbox::request_result`, polled each frame, `Shell::poll_format_request`). A failed write ends nothing: the Warning notice `The format request was not saved, so nothing is formatted.` and the row disabled with `Not saved` for the rest of the run. The frontend never formats; the storage script checks the disk again at the next boot (`os/README.md`). The Warning notice of a share in RAM ends with `Settings > System can format it.` when there is an offer. After a request, `share_format` gives the Info notice `The share partition is formatted.` or a Warning with the reason.
- The input notices (`docs/spec/input-generic-pads.md`): each frame, `Shell::poll_pads` takes the notices of the input source (`PadRoster::take_notices`) and logs each one. The notice of a pad with the generic layout, of a joystick that is not a gamepad and of a pad with no free port also goes to the player, once per pad per plug (`pad_notes.rs`): a pad is told when the player answers its notice, so a notice that waits in a game for the quick menu shows again in the next run when the run ends first. The notice of the generic layout has the button `Set up this controller`, which starts the guided mapping of the pad in the game list, and in a game opens the Input panel with the focus on the row of the pad (`Screens::open_panel`). A dropped notice (the list holds 8) is not told, so the next notice of its pad shows. The silent pad rule (`neptron_input::SilentPads`) runs on the activity of the source and the button presses of the frame, and tells only in the game list. The pads told and checked are in `run/pad-notes.toml` (RAM folder), written whole by the writer thread (`Job::PadNotes`) when the list grows, and read at boot; a damaged file reads as empty. The KMS backend forwards the notices of the gamepads and of the keyboards.
- The Input panel (`Settings > Input`, `pages::input_page`, `docs/spec/input-players.md`) shows the pad of each of the four players, with `(away)` for a pad that went away in a game, one `Extra pad` row for each pad on ports 4 to 7, the keyboard (player 1), and `Hold Start for menu`. A present pad with the generic layout shows `(generic layout)` after its name, and a pad with a map of the player `(your layout)`. The row of a present pad opens the page of its controller (`SettingValue::Link`, `pad_page.rs`). A pad name is cut with `...` so the row fits, and a character the font does not have shows as `?`. The shell reads the roster of its input source (`InputSource + PadRoster`) when it builds the page, and builds it again when the roster counter changes (`Shell::poll_pads`). The pads open with the rule of the run: `PortRule::Game` in a game run, `PortRule::Menus` otherwise, and with the roster of the relaunch file held on their ports.
- The controller layouts of the player (`docs/spec/input-remapping.md`): `pad_maps.rs` reads `config/input/pads.toml` at the start of each run, before the first poll, and gives the maps to the input source (`PadRoster::set_player_maps`). A write changes only the `[[pad]]` table of one identity and keeps every other table and unknown key; an entry with `system` or `game` is skipped and kept; an identity is compared as a value; a damaged or newer file, or one whose `pad` key is not a list, gives a notice, is never written, and disables `Map buttons` and `Reset to default`. The text of the file is made before the layouts change, so a text that cannot be made writes nothing. The writer thread writes it whole (`Job::PadMaps`). The page of a controller (`pad_page.rs`, one page id per port) shows its name, its kind of layout, `Map buttons`, `Reset to default` and the binding of each control, from `PadRoster::pad_map`. `shell/mapping.rs` runs the guided mapping in the game list only: the source captures the pad, `neptron_input::GuidedMapping` reads its raw state each frame, the snapshot shows the prompt (built again only when its text changes), and the end puts the map on trial for 15 s in the review. Keep stores it; cancel, back from another device, a timeout or a pad that goes away gives the old maps back. In a game the page is read only.
- The Network panel (`Settings > Network`, `pages::network_page`, `docs/spec/network-panel.md`) holds information rows only: the address of each wired port, the host name, the state of the share and, with the share on, `<host_name>.local` (`mdnsd` runs only with the share), the share path for Windows and for macOS and Linux, and the published account. With an empty or invalid host name the name rows go and the share paths use the first address. The thread `network-watch` (`network.rs`) reads `/run/neptron/network.toml` (parsed by `neptron_platform::parse_network`) and the share switch `/state/network-share-off`. The thread reads at most 64 KiB of the file. The frame thread asks for a read at the start, in the first frame the panel is on screen, and every second (`NETWORK_REFRESH_NS`) while it stays there (the screen on show of the last frame decides, `NETWORK_SCREEN`; the snapshot keeps the page after the panel closes), over a channel of one request that merges a second one; the thread sends a result only when it changed, and the frame thread takes it with `try_recv` (`Shell::poll_network`) and builds the panel again. So a late lease shows with no need to leave the panel. A missing, damaged or newer file, or a reader thread that did not start, gives the one row `Address` `Not known` and a log line with the reason, never a notice. `Shell::network_counts` gives the reads asked for and the pages built, for the tests. The shell owns the thread; drop ends and joins it.
- The set check of an arcade game (`docs/spec/arcade.md`, section 10). A launch of a game of the core `fbneo` starts the thread `neptron-set-check`, which the library owns (`Library::start_check`; drop cancels and joins it). The thread lists the central directory of each zip of the set, its parent and its BIOS that it finds in the folder of the game, `share/bios/fbneo` and `share/bios`, in that order (`neptron_session::zip_entries`), and looks for a file at each path of `arcade::disk_paths` for the disk images of the set (presence only: an image is not read). `neptron_library::arcade::check_set` decides. The frame thread polls the result (`Shell::poll_set_check`) and never waits; a second launch while a check runs is ignored. A set that passes ends the run with the relaunch. A set that fails gives a Warning notice with the message of the check, with no mode change and no relaunch. With no arcade index the notice asks: `Cancel` (the focus) or `Start`, which relaunches into the game unchecked. The ROMs that are missing or differ go to the log.
- Every write (settings, the guard record, the library cache) goes to the writer thread (`outbox.rs`) over a bounded channel. A full channel keeps the job in a backlog on the frame thread, in order; nothing is dropped. The frame thread does no file I/O.

## Control protocol

`control.rs`: the socket thread accepts one connection at a time (read and write timeouts of 2 s, socket file mode 0600) and sends each command to the frame thread over a bounded channel. The frame thread answers between two frames. `wait` stays on the frame thread until its condition holds or its time ends; a `timeout_ms` above 60 s (`WAIT_TIMEOUT_MAX_MS`) is cut to it. At the end of a run `ControlServer::stop` answers every open wait and queued command with `unavailable`, closes the frame thread's side, and stops the socket thread, which ends a connection between two request lines, so a waiting or busy client never delays the end of a run.

| Command | Served |
| --- | --- |
| `hello`, `ui_tree`, `session_state`, `video_state`, `stats`, `settings_get`, `log_tail` | Always |
| `input_send`, `input_script`, `session_launch`, `settings_set` | With the `control` feature. A display setting goes through the guard, as a menu choice does |
| `wait` | Always, on the frame thread |
| `clock_step` | `unavailable`: the binary runs in real time. The tier 2 tests step the simulated clock themselves |
| `screenshot` | `unavailable`: the frontend has no PNG encoder |

## The log and the stop

- The lines of the protocol log (guard events, notices, every mode set with its read back) also go to the log of the run. The frame thread queues each line in a bounded channel (`logbook.rs`, 256 lines) and never waits: a full channel drops the line and counts it. A writer thread writes the lines to standard error; a failed write loses the line and never stops the run or panics. At start the log names the binary and the folders.
- SIGTERM and SIGINT set a stop flag (`stop.rs`), registered before any SDL code starts, so SDL3 installs no handler of its own for them. The frame loop reads the flag at each frame and ends the run as a quit: save RAM and settings written, the display dropped by its rules, exit code 0.

## Must never depend on

- Logic of its own: logic belongs in the crates

## Rules

- `unsafe` is forbidden: the crate root carries `#![forbid(unsafe_code)]`.
- Features: `kms` (Linux: KMS, SDL3 gamepads and audio, evdev keyboards), `window` (SDL3 window and audio), `control` (the commands that change the frontend). No feature is on by default.

## Open points

- The output connector is not an input of the guard, and a new connector needs the display opened again, so the display panel shows it read-only and `settings_set display.output` is refused. It changes in `global.toml` or `neptron.toml` and takes effect at the next start, where the guard record's output check below opens the boot prompt.
- `screenshot` is not served: the frontend has no PNG encoder.
- Favourites and recent games are not kept; their lists are empty.
- The KMS build: `Detected::backend_caps` gives the caps of the display, by the output kind (`OutputKind`, ADR 0010). The output is digital only when the class rule finds a flat panel on a digital link and `display.monitor` gives that panel (`auto` or `flat`); every other case is analog: no EDID, a CRT, a DAC, `flat` on an analog output, a CRT preset on a digital output. An analog output gets the table's caps, and buffers of 2560x1200 at most cut to them, as before panels. A digital output gets the table's digital limits for its connector (`Matrix::caps_for_output`), and buffers that also hold the panel's largest listed mode up to 3840x2160, cut to those limits. The caps carry the buffer size as the largest mode, so the boot cuts the panel's modes to the buffers. The validator is unchanged: a panel mode must be one of its listed modes, inside these caps; the kernel's test-only commit is the last word, and a refused mode falls to the next listed one. The connector rule gets the class of `display.monitor`. Before the display opens the subconnector is not known, so a DP connector with a digital EDID opens with the digital caps. Right after the open, the class of the driven connector is read again with its subconnector; when the output is analog (a `VGA` subconnector, or a digital adapter with no EDID), `Detected::policy_caps` and `KmsDisplay::lower_caps` cut the caps of the policy and the validator to the analog ones. No CRT path runs with the digital limits; only the buffers stay larger. The GPU caps come from the output of the settings, else the connector that gave the profile, else the first connected output. A 3840x2160 XRGB8888 buffer is 33 MB, and the GBM surface has at most four.
- Only `intel_gen9` has digital limits today: 300 MHz on HDMI, 165 MHz on DVI-D, 533.25 MHz on DP, 4096x2160. Every other GPU gives a digital output its analog values (165 MHz, 1920x1200), so a 1440p or 4K panel there runs in its largest listed mode of at least 50 Hz that fits, usually 1080p60, with a notice.
- An adapter that shows its own digital EDID with a CRT behind it, and no analog subconnector, is taken for a flat panel. ADR 0013 accepts that it gets the panel mode with no prompt. The protection: a monitor preset in `display.monitor` always wins, is never trusted, and makes `generic_15` the safe default, so its boot prompt reverts to 15 kHz.
- The menu source is 60 Hz also on a 50 Hz profile; the policy picks the mode.
- `video_state` gives an empty `verdicts` list.
